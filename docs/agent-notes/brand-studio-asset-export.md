# Asset export (brand-studio)

All asset image export is **client-side DOM capture** (`html-to-image`), not server-side. The server has no way to render templates to images, so any "email/attach the assets" feature must have the browser generate the bytes and send them up.

- Still templates: captured via `TemplateRenderer` + `SIZE_CONFIGS` (`captureAssetAsPng/Jpg` in `src/lib/gifExport.ts`).
- **HTML assets**: both `html_banner` AND `animated_social` are now self-contained HTML stored in `asset.htmlContent` (generated by `generateHtmlBanner`; `animated_social` passes `dimensions:{1080,1080}` + `animated:true` so looping CSS animation is a hard prompt requirement). They render via sandboxed `<iframe srcDoc>` (sanitize with DOMPurify where shown), NOT TemplateRenderer.
- **Legacy `animated_social`** rows predate this and have `isAnimated:true` + `htmlContent:null`; they still fall back to `TemplateRenderer` (CSS overlay) + GIF (`captureAnimatedAssetAsGif`). Regenerating such a row now backfills `htmlContent`.

**Unifying rule — key off `asset.htmlContent` presence, not `templateSize`:** treat any asset with `htmlContent` as HTML for display (iframe) and export. ZIP: `isAnimated && htmlContent` → `.html` (preserves motion) BEFORE the legacy `isAnimated` → GIF branch; `html_banner` stays PNG (its export was intentionally left unchanged). PDF excludes `isAnimated`.

**Native dims gotcha:** `html_banner` is NOT in `SIZE_CONFIGS`, so `getTemplateConfig("html_banner")` returns a wrong fallback — special-case it to 728×90; `animated_social` IS in `SIZE_CONFIGS` (1080×1080) so `getTemplateConfig` is correct for it. Any export loop that treats "not animated" as "render via TemplateRenderer" will silently produce a wrong fallback template for `html_banner`, so branch on `templateSize === "html_banner"` / `htmlContent` first.
